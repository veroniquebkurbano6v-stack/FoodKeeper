## 一、改进总览

通过对项目源代码的完整审阅，识别出以下几类核心问题：

| 问题类别 | 问题数量 | 影响 |
|---------|---------|------|
| **架构混乱** | 4 | 两套前端并行、配置不一致、部署易出错 |
| **功能未完成** | 6 | 采购计划是 Mock、出库日志表未对接、口味偏好表未对接等 |
| **数据安全风险** | 5 | Token 内存存储、登出未清 Token、API Key 明文存 localStorage 等 |
| **交互体验不足** | 8 | 无 PWA、无离线、无快捷键、无撤销等 |
| **AI 体验可优化** | 5 | 等待时间长、无进度反馈、无自定义菜谱数量等 |
| **视觉一致性** | 3 | 水产和速冻同色、移动端字号小等 |

下文按模块逐项给出具体改进建议。

## 二、架构与产品定位层

### 2.1【P0 / 中难度】统一两套前端，明确产品定位

**当前问题**：
项目存在两套前端，造成混乱：
- 前端 A（`src/`）：Vue3 + Vant 4 + LocalStorage，纯前端 Demo，功能丰富但无后端
- 前端 B（`frontend/`）：Vue3 + TS + Element Plus + Axios，对接后端但功能较少

两套前端功能不对等、UI 风格迥异、文档易混淆，新手难以选择。

**改进建议**：
1. 明确产品定位：是「轻量个人本地工具」还是「多用户云端服务」？
2. 若定位为个人工具：保留前端 A，废弃前端 B，后端仅作为可选的同步后端
3. 若定位为多用户服务：以前端 B 为主，将前端 A 的功能（AI 菜谱、报表、日志、偏好）迁移到前端 B
4. 在 README 顶部明确说明当前主推版本，避免用户困惑

### 2.2【P0 / 低难度】修复配置不一致问题

**当前问题**：
- `application-prod.yml` 后端端口为 **8082**
- `docker-compose.yml` 暴露 **8080**
- 容器内运行 `--spring.profiles.active=prod` 时实际监听 8082，但 Dockerfile 健康检查访问 8080 → 健康检查会失败

**改进建议**：
统一生产端口为 8080，或在 docker-compose 中映射 `8082:8082`，并同步更新 Dockerfile 健康检查命令。

### 2.3【P1 / 中难度】K8s deployment.yml 去除 Helm 模板语法

**当前问题**：
`k8s/deployment.yml` 包含 `{{ include ... }}` Helm 模板语法，直接 `kubectl apply` 会报错，但 README 没有明显提示。

**改进建议**：
1. 提供纯 kubectl 版本和 Helm Chart 版本两套文件
2. 在 `k8s/README.md` 顶部用 ⚠️ 醒目标注此限制
3. 或将模板语法替换为 Kustomize patches

### 2.4【P1 / 低难度】补充 `.env.example` 说明

**当前问题**：
`.env.example` 列出了所有变量但未说明哪些必改、哪些可保持默认。

**改进建议**：
在 `.env.example` 文件中添加注释分组：
```bash
# === 必须修改（生产部署）===
JASYPT_PASSWORD=prod-secret-key-change-me    # 配置加密密钥
MYSQL_PASSWORD=food123                       # 数据库密码
MYSQL_ROOT_PASSWORD=root123                  # 数据库 root 密码
IMAGE_PREFIX=your-github-username/food-inventory  # 镜像前缀

# === 可选（按需调整）===
MYSQL_PORT=3306
REDIS_PORT=6379
BACKEND_PORT=8080
FRONTEND_PORT=80
```

## 三、食材管理模块

### 3.1【P0 / 中难度】添加食材拍照存档功能

**当前问题**：
- `FoodDO` 实体未设计 `photo` 字段（虽然前端 A 的 store 中有 photo 字段但从未写入）
- 需求清单 F1 明确要求「拍照存档」
- 用户难以记住某次采购的具体食材外观

**改进建议**：
1. 数据库 `food` 表新增 `photo_url VARCHAR(255)` 字段
2. 前端新增食材时支持拍照或选择图片（移动端用 `<input accept="image/*" capture="environment">`）
3. 图片存储：Demo 版用 Base64 存 localStorage（限制大小 ≤ 200KB），生产版上传 OSS 或本地文件服务
4. 食材卡片缩略图展示，详情页大图查看

### 3.2【P1 / 低难度】保质期天数自动填充覆盖不全

**当前问题**：
`stores/inventory.js` 的 `defaultExpiryDays` 仅覆盖少量常见食材（西红柿 7 天、猪肉 5 天等），输入未匹配的食材时保质期天数字段为空，用户需手动查询。

**改进建议**：
1. 扩充 `defaultExpiryDays` 字典，至少覆盖 50 种常见食材
2. 提供按分类的默认值兜底（如蔬菜默认 5 天、肉类默认 3 天、冷冻默认 180 天）
3. 用户输入未匹配食材时显示「该分类常见保质期 X-Y 天」提示
4. 允许用户将当前输入的食材+天数保存到自定义字典

### 3.3【P1 / 中难度】分类与存放分区扩展

**当前问题**：
- 前端 A 只有 5 个分类（蔬菜/肉禽蛋奶/水产/干货调料/速冻食品）
- 后端 SQL 初始化了 8 个分类（蔬菜/肉类/海鲜/干货/冷冻/调料/水果/饮料）
- 前端 A 缺少「水果」「饮料」分类，用户无法正确归类
- 存放分区只有 3 个（冷藏室/冷冻层/常温），缺少「保鲜室」「门栏」等细分

**改进建议**：
1. 前后端分类统一为 8 个，与后端 SQL 对齐
2. 新增「自定义分类」功能，允许用户添加个性化分类
3. 存放分区增加「保鲜室」「门栏」「干货柜」等选项
4. 用户可设置常用分类，置顶显示

### 3.4【P2 / 低难度】食材批量操作

**当前问题**：
所有食材操作都是逐个进行，缺少批量能力：
- 无法批量删除已过期食材
- 无法批量修改存放分区
- 无法批量导出某分类食材

**改进建议**：
1. 库存列表增加多选模式（长按或右上角「编辑」按钮进入）
2. 支持批量删除、批量修改分区、批量导出选中项
3. 临期页支持「全部已过期一键报废」操作

### 3.5【P2 / 中难度】食材搜索增强

**当前问题**：
当前仅支持按食材名称模糊搜索，无法满足复合查询需求。

**改进建议**：
1. 增加按存放分区筛选
2. 增加按价格区间筛选
3. 增加按采购日期区间筛选
4. 增加「仅看临期」「仅看低库存」快速筛选开关
5. 搜索历史记录与智能推荐

## 四、临期预警模块

### 4.1【P0 / 中难度】新增推送通知功能

**当前问题**：
临期预警完全依赖用户主动打开应用查看，用户不打开就不知道有食材要过期，违背了「预警」的核心价值。

**改进建议**：
1. **PWA Push 通知**：集成 Web Push API，用户授权后每天早上推送当日临期食材清单
2. **邮件提醒**：标准版后端集成邮件服务，每天定时扫描并发送临期邮件
3. **微信/钉钉机器人**：webhook 推送到家庭群
4. **应用内小红点**：tabbar「首页」角标显示临期数量
5. **首页强提醒**：进入应用时若有 ≤2 天临期食材，弹出确认对话框

### 4.2【P1 / 低难度】临期阈值可配置

**当前问题**：
临期分级阈值硬编码在前端 `utils/index.js`（≤2 天=red，≤7 天=yellow，>7=green），不同家庭对「临期」定义不同。

**改进建议**：
1. 设置页新增「临期阈值配置」分组
2. 用户可自定义 red/yellow 阈值（如「3 天内为即将过期，10 天内为临期」）
3. 配置存入 `systemConfig`，全局生效

### 4.3【P1 / 中难度】过期食材自动处理流程

**当前问题**：
已过期食材会一直留在库存中（quantity 不变），用户需要手动报废。若用户长期不打开应用，过期食材会堆积。

**改进建议**：
1. 系统每日巡检时自动将已过期 7 天以上的食材自动报废（写入 outboundType=auto-discard 日志）
2. 设置页提供「自动报废天数」配置项（默认 7 天）
3. 报表页新增「自动报废统计」指标
4. 自动报废前 1 天推送提醒「明天将自动报废以下食材」

### 4.4【P2 / 低难度】临期食材的食用建议

**当前问题**：
临期预警页只展示食材列表，不告诉用户「该怎么处理」，用户看到临期食材后仍需自己思考。

**改进建议**：
1. 临期卡片底部增加「快速做菜」按钮，点击跳转 AI 菜谱页并自动将该食材作为优先推荐项
2. 卡片增加「保存技巧」展开项，提示「可用保鲜膜包裹延长 2 天」「可冷冻保存」等
3. 已过期卡片增加「能否继续食用」判断提示（如「酸奶过期 1 天可继续食用，但需观察气味」）

## 五、AI 菜谱推荐模块

### 5.1【P0 / 高难度】降低 AI 生成等待焦虑

**当前问题**：
- 生成 5-6 道菜谱耗时 20-40 秒，用户等待期间只有 spinner 和计时器，焦虑感强
- 无进度提示，用户不知道还要等多久
- 单次请求失败需重新生成，浪费 token

**改进建议**：
1. **流式输出（Streaming）**：所有服务商都支持 SSE 流式响应，逐字输出菜谱内容，首道菜谱 5 秒内可见
2. **分批生成**：先生成 1 道菜谱立即展示，后台继续生成剩余 4-5 道
3. **进度条**：根据已用时间显示进度条（0-10s 30%，10-20s 60%，20-30s 90%，30s+ 99%）
4. **预估耗时**：基于历史生成耗时显示「预计还需 X 秒」
5. **等待时内容**：展示「今日临期食材」「营养小知识」等内容转移注意力
6. **失败重试**：网络中断时自动从断点继续，而非重新生成

### 5.2【P1 / 中难度】菜谱个性化与反馈机制

**当前问题**：
- 用户无法对生成的菜谱表达喜好（喜欢/不喜欢）
- AI 不知道用户历史反馈，每次生成都从零开始
- 菜谱类型分类（quick/healthy/home）较粗，无法满足细分场景

**改进建议**：
1. 菜谱卡片增加「👍 喜欢」「👎 不喜欢」按钮，记录到 localStorage
2. 增加菜谱场景细分：早餐 / 午餐 / 晚餐 / 夜宵 / 一人食 / 家庭餐 / 待客菜
3. 生成时优先包含用户「喜欢」过的菜谱或相似菜谱
4. 「不喜欢」的菜谱加入黑名单，后续不再生成
5. 增加菜谱难度分级更细：零基础 / 简单 / 中等 / 困难
6. 支持「再来一道相似的」按钮，基于当前菜谱推荐相似菜谱

### 5.3【P1 / 低难度】菜谱数量与营养目标可配置

**当前问题**：
菜谱数量硬编码为 5-6 道，无法满足不同家庭规模（1 人 vs 4 口之家）和不同场景（一顿 vs 一周）的需求。

**改进建议**：
1. 生成前选择「人数」（1/2/3-4/5+），AI 据此调整食材用量
2. 选择「菜谱数量」（3/5/8/10）
3. 设置「营养目标」（减脂/增肌/均衡/高蛋白/低碳水），AI 据此筛选菜谱
4. 设置「烹饪时长上限」（15/30/60/不限分钟）
5. 这些配置存入 preferences，下次生成自动应用

### 5.4【P1 / 中难度】菜谱与库存的闭环联动

**当前问题**：
菜谱生成后与库存无联动：
- 看了菜谱去烹饪后，库存不会自动扣减
- 「需购买食材」不会进入采购计划页
- 烹饪后无法反馈「这道菜用了哪些食材、扣多少库存」

**改进建议**：
1. 菜谱详情页新增「开始烹饪」按钮：
   - 自动从库存扣减冰箱已有食材的数量
   - 弹窗让用户确认扣减量（可调整）
   - 写入 outboundType=cook 日志，备注菜谱名
2. 菜谱详情页新增「加入采购计划」按钮：
   - 将「需购买食材」自动写入采购计划页
   - 采购完成后回到菜谱页可继续烹饪
3. 烹饪完成后邀请用户评价菜谱（星级 + 文字），影响后续推荐

### 5.5【P2 / 中难度】菜谱分享与社区

**当前问题**：
菜谱仅个人可见，无法分享给家人或朋友，缺乏社交属性。

**改进建议**：
1. 菜谱详情页新增「分享」按钮：
   - 生成菜谱卡片图片（含菜名、食材、步骤摘要）
   - 复制菜谱文本到剪贴板
   - 生成分享链接（标准版后端存储菜谱数据）
2. 「我的菜谱」支持导出为 PDF / 长图
3. 后续可考虑「菜谱广场」社区功能（用户上传菜谱、点赞、收藏）

## 六、出库与日志模块

### 6.1【P0 / 中难度】出库日志后端持久化

**当前问题**：
- 数据库 `outbound_log` 表已建但无对应 DO/Mapper/Service
- 后端 `outboundFood` 接口只减库存，不写日志
- 前端 B 用户的所有出库操作无日志可查
- 前端 A 的日志仅存 localStorage，清缓存即丢失

**改进建议**：
1. 新增 `OutboundLogDO`、`OutboundLogMapper`、`OutboundLogService`
2. `FoodServiceImpl.outboundFood` 改造为事务性写入日志
3. 新增 `OutboundLogController` 提供 `GET /api/outbound/log/list` 分页查询接口
4. 前端 B 增加出库日志页面，对接后端
5. 支持按日期范围、食材名、出库类型筛选

### 6.2【P1 / 低难度】出库操作撤销机制

**当前问题**：
所有出库操作不可撤销，用户误操作后只能重新入库，体验差。

**改进建议**：
1. 出库后显示 Toast「已出库 X 件」+ 「撤销」按钮（5 秒内可点击）
2. 日志页每条记录增加「撤销」按钮，点击后恢复数量并标记日志为「已撤销」
3. 撤销操作有限制：只能撤销 24 小时内的操作；已报废的食材无法撤销
4. 撤销操作也写入日志，备注「撤销 ID=xxx 的出库」

### 6.3【P1 / 中难度】烹饪消耗与菜谱联动

**当前问题**：
当前烹饪出库完全靠用户手动选择食材和数量，与菜谱脱节。用户看完菜谱后还要去出库页挨个选食材，繁琐。

**改进建议**：
1. 出库页新增「从菜谱出库」入口
2. 选择菜谱后自动列出该菜谱所有「冰箱已有食材」
3. 用户确认后一键批量扣减
4. 自动写入出库日志，备注菜谱名
5. 若库存不足，提示「X 食材库存不足，是否部分出库？」

### 6.4【P2 / 低难度】出库日志筛选与导出

**当前问题**：
- 日志筛选只有 4 个 Tab（全部/cook/discard/clear），无法按日期、食材、数量筛选
- 无法导出日志做月度复盘

**改进建议**：
1. 增加日期范围筛选（今天 / 近 7 天 / 近 30 天 / 自定义）
2. 增加食材名搜索
3. 增加数量范围筛选
4. 日志页右上角「导出」按钮，支持 CSV 导出（含食材名、类型、数量、原因、日期）

## 七、采购计划模块

### 7.1【P0 / 高难度】采购计划完全重构

**当前问题**：
`ShoppingPlan.vue` 是半成品：
- 缺料清单是硬编码 Mock 数据（姜蒜/生抽/葱花/醋/豆腐/香油）
- 与 AI 菜谱的「需购买食材」完全脱节
- 无智能采购建议
- 无采购历史记录

**改进建议**：
1. **缺料自动汇总**：扫描所有收藏菜谱的「需购买食材」，去重合并，生成缺料清单
2. **库存低于阈值提醒**：用户可为每个食材设置「最低库存」，低于时自动加入采购计划
3. **历史采购记录**：记录每次采购的食材、数量、价格、采购日期，用于价格趋势分析
4. **智能采购清单**：
   - 按超市分类（生鲜区/调料区/冷冻区）排序
   - 标注预估价格区间
   - 标注「上次采购 X 天前，价格 ¥Y」
5. **采购完成回调**：标记「已买」后自动入库（数量、单价可编辑）
6. **共享清单**：标准版支持家庭共享采购清单，多人协作

### 7.2【P1 / 中难度】价格趋势与比价

**当前问题**：
用户记录了食材单价，但未用于分析。无法知道「猪肉这几个月涨价了吗」「哪个超市便宜」。

**改进建议**：

2. 同一食材不同采购记录的价格对比
3. 价格异常波动提醒（如某次采购价格比平均高 30%）
4. 标准版后端可对接外部价格 API（如超市价格数据）

### 7.3【P2 / 低难度】采购清单模板

**当前问题**：

**改进建议**：

## 九、设置与数据管理模块

### 9.1【P0 / 高难度】数据云端同步

**当前问题**：
前端 A 数据完全存 localStorage，存在严重风险：
- 清浏览器缓存数据全丢
- 换设备数据不互通
- 无法多端访问
- 无自动备份

**改进建议**：
1. **标准版对接后端同步**：登录后自动将本地数据同步到后端
2. **冲突解决**：多设备编辑时按 updatedAt 时间戳合并，或提示用户选择版本
3. **增量同步**：仅同步变更项，减少流量
4. **离线优先**：网络断开时正常使用本地数据，恢复后自动同步
5. **自动备份**：后端每日定时备份到对象存储（OSS/S3）

### 9.2【P0 / 中难度】API Key 安全存储

**当前问题**：
- API Key 明文存 localStorage，任何能访问浏览器的脚本都能读取
- 浏览器扩展或 XSS 攻击可窃取 Key
- 一旦泄露，攻击者可滥用用户的 AI 额度

**改进建议**：
1. **标准版后端代理**：Key 加密存后端数据库（Jasypt），前端请求经后端转发，浏览器永远拿不到原始 Key
2. **前端加密存储**：Demo 版用用户密码派生密钥加密 Key 后存 localStorage
3. **Key 一次性输入**：每次会话输入 Key，关闭浏览器即清除（不持久化）
4. **使用提醒**：保存 Key 时弹窗提示风险，让用户知情同意
5. **额度监控**：后端记录每次 AI 调用，异常使用时告警

### 9.3【P1 / 中难度】Token 安全性增强

**当前问题**：
- Token 存内存 `ConcurrentHashMap`，重启即失效
- 登出接口未实际清除 Token
- Token 无过期时间
- 开发模式所有用户默认 SUPER_ADMIN + 通配权限，存在越权风险
- Redis 后备机制未实际启用

**改进建议**：
1. Token 存 Redis，设置 7 天过期，支持滑动续期
2. 登出接口实际清除 Token（Redis + 内存）
3. 移除开发模式的默认超管权限，改为基于数据库角色表的真实权限
4. 引入 Refresh Token 机制，Access Token 短期（2 小时），Refresh Token 长期（7 天）
5. 异地登录检测，踢掉旧会话
6. 敏感操作（删除/重置密码）要求二次密码验证

### 9.4【P1 / 低难度】数据导入功能

**当前问题**：
设置页支持导出 JSON/CSV，但不支持导入。用户换设备时只能手动重新录入。

**改进建议**：
1. 设置页新增「导入数据」入口
2. 支持 JSON 导入（结构校验 + 字段映射）
3. 支持 CSV 导入（智能识别列）
4. 导入前预览数据，确认后覆盖或合并
5. 导入冲突处理策略：跳过 / 覆盖 / 重命名

### 9.5【P2 / 低难度】主题与字号可配置

**当前问题**：
- 主题固定为「暖意厨房」，无法切换
- 字号固定，老年用户看不清
- 无深色模式

**改进建议**：
1. 设置页新增「主题切换」：暖意厨房（默认）/ 极简白 / 深色模式 / 跟随系统
2. 字号调节：小 / 中 / 大 / 特大（影响全局文字大小）
3. 自定义主色调（提供 6 种预设色）
4. 减少动画开关（无障碍友好）

## 十一、性能与可靠性层

### 11.1【P0 / 中难度】PWA 离线支持

**当前问题**：
- 应用依赖网络加载，断网无法访问
- 无 Service Worker 缓存
- 无 manifest，无法「添加到主屏幕」

**改进建议**：
1. 集成 `vite-plugin-pwa`
2. 配置 manifest：name、short_name、icons、theme_color、display: standalone
3. Service Worker 缓存策略：
   - 应用 shell：Cache First
   - 图片：Cache First + 后台更新
   - AI 请求：Network Only（无法离线）
4. 离线提示：断网时顶部显示「离线模式，部分功能不可用」
5. 「添加到主屏幕」引导弹窗

### 11.2【P1 / 中难度】大数据量性能优化

**当前问题**：
- 前端 A 所有数据存 localStorage，单 key 存储，食材数量超过 500 时性能下降
- 库存页一次性渲染所有食材卡片，无虚拟滚动
- localStorage 单 key 容量约 5MB，大量食材+日志可能超限

**改进建议**：
1. 库存页引入虚拟滚动（vue-virtual-scroller），仅渲染可视区域卡片
2. 分页加载：默认显示 20 条，滚动到底部加载更多
3. localStorage 分 key 存储：`foods:vegetable`、`foods:meat` 等，按分类隔离
4. 数据量超阈值时提示用户导出备份并清理旧日志
5. 标准版改为后端分页查询，前端只缓存当前页

### 11.3【P1 / 低难度】AI 请求缓存与去重

**当前问题**：
- 每次点击「生成菜谱」都重新请求 AI，即使库存未变化也浪费 token
- 用户频繁点击会触发多次请求

**改进建议**：
1. 生成前计算库存签名（食材名+数量+临期状态的 hash）
2. 若签名与缓存一致，提示「库存未变化，是否使用上次结果？」
3. 防抖：点击生成后 5 秒内禁用按钮，防止重复点击
4. 请求取消：新请求发起前取消上一个进行中的请求
5. 失败重试机制：网络错误自动重试 1 次（间隔 2 秒）

### 11.4【P2 / 中难度】后端接口性能优化

**当前问题**：
- 食材列表查询未走索引覆盖（SELECT 多字段）
- 用户列表分页查询用 JOIN，数据量大时慢
- 无缓存层

**改进建议**：
1. 食材列表增加复合索引 `(category_id, expiry_date, deleted)`
2. 用户列表查询拆分：先查主表分页，再批量查询关联信息
3. 引入 Redis 缓存：分类列表、常用食品列表等低频变更数据缓存 5 分钟
4. 接口响应压缩：开启 Gzip
5. 数据库连接池监控

### 11.5【P2 / 低难度】错误监控与日志收集

**当前问题**：
- 前端错误仅 console.error，开发者无法感知用户遇到的报错
- 后端日志仅本地文件，无集中收集

**改进建议**：
1. 前端集成 Sentry（开源版可自建 GlitchTip），自动捕获 JS 错误
2. 关键操作埋点：食材入库、AI 生成、出库等，统计功能使用率
3. 后端日志收集：Filebeat → Elasticsearch → Kibana
4. 用户反馈入口：设置页「反馈」按钮，提交截图+描述
